# python/tools/sim — Warp GPU simulation stack

This is the active development area. It implements a GPU FEM elastodynamics solver with augmented-Lagrangian (SAL) contact in **NVIDIA Warp** (plus cupy and `cuda.compute`/cuda-cccl for scans, reductions and sorts). Each solver mirrors a C++ algorithm in `source/pbat/sim/algorithm/` (see `source/pbat/sim/CLAUDE.md`). The two sides should agree closely but don't have to match exactly. When they diverge, check whether it's intentional before "fixing" either side.

Pinned dependencies are in `requirements.txt` (warp-lang, cupy, cuda-cccl, polyscope, h5py, ...). `pbatoolkit` must also be installed, built from this repo; see the `pbat-build` skill.

## Running

All commands run from the repo root, as modules:

```bash
python -m python.tools.sim.ui --fem-elasto-dynamics scene.h5:group/path [--sim-params params.toml ...] [--set Solver.VBD.gtol=1e-4]
python -m python.tools.sim.gpu.elasticity.fem     # modules with a unittest.TestCase run their tests via __main__
python -m unittest python.tools.sim.gpu.vbd.params
```

- Code layout: `state.py` holds `SimulationState`, the loaders and the HDF5 (de)serialization, shared by `ui.py` (GUI) and `simulate.py` (headless). GUI features live in `panels/<feature>.py` (see `panels/__init__.py`). Profiling scopes come from `gpu/common/profiling.py`.
- The UI is interactive (Polyscope + imgui), so Claude can't drive it. Use the headless counterpart instead:

  ```bash
  python -m python.tools.sim.simulate --fem-elasto-dynamics data/CubeFallingOnCube.Dump.h5:fem -o out.h5 [--sim-params p.toml ...] [--set KEY=VALUE] [--solver AndersonSolver] [--cd VertexSdf] [--duration 2] [--fps 60]
  ```

  It reuses `state.SimulationState` and the GUI's parameter (de)serialization. Its output uses the same layout as the GUI's Serialization feature:
  - `FemElastoDynamics/{X,E,m,dmask,...}`
  - `sim/<frame:08d>/x`, with the frame's time step count as the attribute `t`
  - `params/` holding `fps`, `solver` and `cd` attributes, plus the full parameter groups.
- **Viewing outputs**: `python -m python.tools.sim.trajectory_viewer a.h5 b.h5 ... [--labels ...] [--reference ref.h5]` plays several outputs of one scene (e.g. one per solver) side by side or overlaid, in sync by simulated time. Colors show speed, body, or the distance to a reference run, and the panel gives the mass-weighted RMS distance per frame and each frame's solve status. The view is framed on the bodies, and static colliders (e.g. huge planes) are translucent points with an opacity slider. Its tests stub Polyscope (`python -m unittest python.tools.sim.trajectory_viewer`).
- **Checkpoints** (`checkpoint.py`) replay a heavy run from just before a failure. `simulate.py --checkpoint-every N` writes the full state every N steps to `<output>.checkpoint.h5`, one `<t:08d>` group per step. `--resume ckpt.h5[:step]` loads the problem and parameters as usual, then restores that step (default: the latest) in place and continues to `--duration` (the total time).
  - Stored: x, v, xtilde, dmask and the BDF history; the kinematic step counter, open anchors and enabled flags; per contact type the AL state with its (u, v) keys, which the next step's warm start reads; the penalties; the vertex SDF's distances; and the active solver's cross-step buffers (the VBD family's `gk`/`xk`/`Hnk`/`betaG`/..., which AAAVBD never resets, plus Chebyshev's and Anderson's histories). GPU Newton has none.
  - Detected pairs aren't stored, since every step detects them again from xt before reading them.
  - The resumed run needs the same problem, contact capacities, `dt`, substeps and BDF scheme. Other parameters may change; with another solver, that solver's buffers start fresh. Its output keeps the uninterrupted run's frame numbers.
  - Test: `python -m python.tools.sim.checkpoint` checks every solver for 2N steps vs. N + checkpoint + resume + N, on two cubes in contact with an open Translate run.
  - Exactness: resuming is bit-exact for the VBD family (BeamFallingOnBeam resumed in contact: all 128 later frames bit-identical for VBD and AAAVBD) and approximate for GPU Newton, which isn't reproducible even straight: two identical BeamFallingOnBeam runs differ from the first step, by up to 5.4 mm over 0.5 s (2026-10-21), and a resumed run differs as much (1.3 mm).
- Instead of `--fem-elasto-dynamics dump.h5:fem`, both `ui.py` and `simulate.py` accept `--scene scene.h5`, a CPU editor scene file (`state.load_scene`, built like the CPU editor through `tools/vbd/scenario.py`). Static mesh and plane colliders become pinned, element-less contact nodes (`colliders.py`), and planes are detected analytically by the vertex SDF (`gpu/contact/mesh/sd.py`, mesh kind `MESH_PLANE`). Infinite planes are half-spaces, while finite planes are plates of their `thickness` (`Sd.set_plane_depths`, fed from `colliders.ContactGeometry`). Dumps carry no colliders. The default adaptive contact penalty (TIMESTEP, `gamman_adaptive = 1`) handles hard impacts on colliders: resting bodies settle at the AL margin `dmin`. Settings come from `--sim-params` or the defaults either way. `reset()` restarts from the rest positions with the loaded initial velocities.
- Example Dump files live in `data/*.Dump.h5` and `data/scenarios/*.Dump.h5`. `data/` is git-ignored but present locally.
- The FEM must already be sorted by connected component. `SimulationState` raises an error otherwise.

## Relationship to `python/tools/vbd` (the CPU predecessor)

`ui.py` is the GPU successor of `python/tools/vbd/`, which pairs an online simulator (`editor.py`) with an offline one (`simulate.py`). Both run the **C++ solvers** through the `pbatoolkit` CPU API, so they're the natural source of reference trajectories when checking GPU results.

- **Input files.** The GPU UI takes as input the HDF5 file written by the editor's **Dump** button (`tools/vbd/ui/simulation.py::_serialize_problem` → `solvers/*.py::serialize_problem`). That file contains the groups `fem`, `contact`, `vbd/params` (plus solver-specific groups such as `vbd/anderson_params`) and `kinematics`, and an `initialization_strategy` metadata entry. Launch with `--fem-elasto-dynamics dump.h5:fem`. Changing how C++ `FemElastoDynamics` (or the dumped `MeshDynamics`/`Params`) serializes therefore affects both tools.
- **Kinematic constraints** (procedurally animated Dirichlet BCs, the editor's `TransformLibrary`) exist on both sides with the same closed-form semantics; see "Kinematic constraints" below. Other editor features may still be missing on the GPU, so check before assuming one exists in `tools/sim`.

## Architecture

**GPU objects are built from CPU objects.** Every GPU object is constructed from its `pbatoolkit` (C++) counterpart. The CPU object owns configuration, adjacency, coloring and (de)serialization. The GPU class copies them into a `@wp.struct` `*Data` and exposes it as `.data` for kernels:

| GPU (Warp) | Built from (pbatoolkit) | C++ reference |
|---|---|---|
| `gpu.elasticity.fem.FemElastoDynamics` | `pbat.sim.dynamics.FemElastoDynamics` | `sim/dynamics/FemElastoDynamics.h` |
| `gpu.integration.bdf.Bdf` | (dt, order) | `sim/integration/Bdf.h` |
| `gpu.vbd.params.Params` / `ChebyshevParams` / `AndersonParams` | `pbat.sim.algorithm.vbd.Params` (+ `ChebyshevParams`/`AndersonParams`) | `sim/algorithm/vbd/{Core,Chebyshev,Anderson}.h` |
| `gpu.newton.solver.Params` | `pbat.sim.algorithm.newton.Params` | `sim/algorithm/newton/Core.h` |
| `gpu.contact.multimesh.MultiMesh` | `pbat.sim.contact.MultiMesh` | `sim/contact/MultiMesh.h` |
| `gpu.contact.dynamics.MeshDynamics` | GPU-only `Params` (DocField) | `sim/contact/MeshDynamics.h` |

Enum values cross the boundary as `wp.constant(int(pbat....Enum.X.value))` (see the `VLS_SOLVER_*` constants in `gpu/vbd/params.py`), so the C++ enums stay the source of truth.

**Solver protocol.** Every solver class (`VbdSolver`, `AaaVbdSolver`, `ChebyshevSolver`, `AndersonSolver`, `NewtonSolver`) implements `solve(fem, contact, cd, params) -> bool` and the property `supports_graph_capture`. Their outer loops have the shape of C++ `vbd::Solve`, except that the outer test is split around the re-detection (see "Convergence and early exit"):

```
initialize_solve → [outer test] → for k < n_max_iters, until it passes: prepare_subproblem
  → solve_subproblem (kp sweeps: contact.update_dual(slack only) → iterate)
  → finalize: full dual update (decay pending) → cd.filter_step → [outer test: gradient, on the solved contact set]
    → cd.detect_contacts → contact.update_constraint_set → [outer test: feasibility, stop] → contact.commit_decay
→ fem.back_substitute_velocities() → cd.on_time_step_ended()
```

Shared steps are defined in `gpu/vbd/solver.py` and imported by the accelerated variants. `linearize_constraints` is still a TODO stub on the GPU. The UI calls `fem.setup_time_integration_optimization(...)` before `solve` and `fem.step()` after it.

**Convergence and early exit.** The VBD-family solvers share `vbd.solver.solve_outer_loop`:
- It tests C++'s criterion `|g_L|^2 <= gtol^2` on the device: g_L is the Lagrangian gradient at the current multipliers, without the AL penalty term (`gpu/vbd/convergence.py::ConvergenceCheck`, built on `gpu/gradient.py::GradientNorm`, which Newton uses in AL form). Between outer iterations its contact force uses the new multipliers with the decay weights gamma the subproblem solved with: the full dual update's weights stay pending (`ConstraintSet.gamma_next`) until `MeshDynamics.commit_decay` after the test, in `solve_outer_loop` and in GPU Newton's `solve`. With `multiplier_step` 1 that equals the subproblem's augmented gradient at the end of its sweeps. **The gradient is measured on the contact set the subproblem solved** (maintainer, 2026-11-06: the AL method solves each subproblem for a fixed constraint set, so measure the problem it tried to solve): after the full dual update and the feasibility filter, before the re-detection and constraint-set update (`ConvergenceCheck.measure_outer_gradient` in `solve_outer_loop`; `newton.solver.outer_gradient_test`), which only stores its scalars; feasibility is measured after the re-detection, on the contacts that see every penetration (`ConvergenceCheck.end_outer`; `outer_feasibility_test`), which then decides the stop and writes the status row; the pending decay weights are committed last, carried across the re-detection by the constraint-set warm start. The last outer iteration still re-detects (it feeds the next step's warm start). Measured after the re-detection (until 2026-11-06), newly detected contacts (lambda = 0) and changed features charged the positions with forces no subproblem had solved for: ArmadilloSpaghetti.DragonImpact AAAVBD 1 x 100 at 7 s recorded 856 and 903 where the solved set's ratio was 16.8, and 141-159 vs 4.0-9.6 over the ten substeps of step 480 (impact window), while on BasketOfFruit (AAAVBD 1 x 80, step 50) the two differ by under 2%; feasibility ratios and positions are unchanged (bit-identical under graph capture on BasketOfFruit, budget-bound). Recorded gradient ratios from before that date are post-re-detection, so don't compare them with newer ones; early exits change where the solved set passes and the re-detected one didn't (trajectories of runs that hit their budget are unchanged). C++ still tests after re-detection (TODO at `vbd::Solve` and `newton::Solve`). Until 2026-11-05 the test read the new weights, charging the positions with the force of contacts reset from gamma < 1 to 1 that they never felt, which overstated BasketOfFruit's recorded ratio 1.2-22x. The test runs between outer iterations and every `ConvergenceParams.check_interval` sweeps (default 20) inside a subproblem. Between outer iterations the step must also be feasible: the largest penetration into the contact margin, max_j max(0, dmin - c_j(x)) over normal contacts only (no friction), must be at most `ConvergenceParams.ftol * max(|dmin|, 1e-6 m)` (`ftol` default 0.5; `convergence.FEASIBILITY_FLOOR`), so a zero or negative margin (the paper configs use `dmin = -1e-4`) still has a positive tolerance and the feasibility ratio stays finite; for the default `dmin = 2e-3` it is `ftol * dmin`. C++ has no such test. **Stationarity test** (dynamic problems; `ConvergenceParams.rstol` 2e-2, `astol` 0.1, `floor_local_kappa` kl = 1.5, `floor_kappa` kg = 0.2; rstol = astol = 0 restores the absolute test; `convergence._is_converged`, `_stationarity_ratios`):

  ```
  RMS_M(q) ≤ 1   and   (RMS_M(q0) ≤ 1   or   RMS_M(r) ≤ kg RMS_M(φ))

  qᵢ       = |rᵢ| / max(ρᵢ, αᵢ, kl φᵢ)
  q0ᵢ      = |rᵢ| / max(ρᵢ, αᵢ)
  rᵢ       = f_res,i / mᵢ = gᵢ / (mᵢ h²)                         residual acceleration
  ρᵢ       = rstol sᵢ / mᵢ                                       relative allowance
  sᵢ       = max(|mᵢ(xᵢ − x̃ᵢ)| / h², |f_el,i|, |f_c,i|, |f_ext,i|)   largest force term
  αᵢ       = max(astol |f_ext,i| / mᵢ, 1e-6 m/s²)                absolute allowance
  φᵢ       = |Hᵢ|_F ε₃₂ |xᵢ| / (mᵢ h²)                             float32 floor
  RMS_M(v) = (Σ mᵢ vᵢ² / Σ mᵢ)^½                                over free nodes
  ```

  sᵢ is the largest term of node i's force balance, each net at the node (inertial, elastic, contact incl. friction as one term, external; `gpu/gradient.py::Gradient` with `force_scale`), h the solve's time step (dt / substeps; `fem.bdf.h`), f_ext,i node i's external force (`fem.data.fext`, read on the device by the ratio kernels, `convergence._absolute_allowance`; host mirror `absolute_allowance`), Hᵢ the vertex Hessian block of the last sweep (`Params.data.Hnk`; VBD stores it like AAAVBD), ε₃₂ = 2⁻²³ (`convergence.ACCELERATION_FLOOR` is the 1e-6). qᵢ is node i's residual over its allowance: relative to its forces (a componentwise relative residual, cf. Oettli-Prager, Arioli-Duff-Ruiz), absolute where the forces are small, or the float32 floor, the acceleration of a one-spacing position error, below which no float32 iterate gets (the exactly rounded solution's residual is ~0.15 RMS_M(φ) on BendingBeam.100MPa and DragonImpact; investigate/float32-residual-floor). The floor clause lets the floor decide only when the residual is near it overall: the per-node floor alone stops a stiff beam's smooth modes early, the global clause alone stops soft bodies when stiff ones set the floor. Every term is a force, so the test doesn't depend on h for a fixed motion; with rstol < 1 and astol < 1 a step that hasn't moved can't pass. The status records RMS_M(q) as `gradient_ratio`, and `max_ratio` (max_i qᵢ), `no_floor_ratio` (RMS_M(q0)) and `floor_clause_ratio` (RMS_M(r) / (kg RMS_M(φ))), so `gradient_ratio` ≤ 1 doesn't mean the test passed; `status_ratio.stationarity_test_ratio` (no GPU imports) gives the decisive max(`gradient_ratio`, min(`no_floor_ratio`, `floor_clause_ratio`)), at most 1 iff it passed, and every viewer of the recorded ratios shows that (the Solve status panel's "Stationarity / tol", `StatusLog.format_summary`, the trajectory viewer, `reference_error`'s `test_ratio`, the profiling report and paper figures), falling back to `gradient_ratio` for rows without the other ratios; the Solve status panel also shows all four, plus the absolute allowance's rule (astol |f_ext,i| / mᵢ per node). GPU Newton runs the same test (2026-11-07; until then it had no floor and tested RMS_M(q0) ≤ 1), Hᵢ the diagonal 3×3 block of its last Newton step's assembled Hessian (`newton.solver._store_hessian_norms`, `warp.sparse.bsr_get_diag`; the same terms as the VBD family's block, but SPD-corrected elastic parts and, with `one_sided_contact`, no normal block on unpressed contacts), and records the decisive ratio as its `gradient_ratio` (`ConvergenceCheck.decisive_ratio`). A solve's tests before its first Newton step have no floor (`newton.solver.initialize_solve`): they test Newton's initial guess xᵗ, which hasn't moved, and on BendingBeam.100MPa kg RMS_M(φ) = 18 m/s² exceeds xᵗ's residual (16–19 m/s²: gravity, vᵗ/h up to 7 m/s², the elastic force's float32 noise), so reading the previous solve's norms there (the VBD family's rule) passed step 2 at xᵗ and froze the beam for good.   **History.** Until 2026-11-06 (dev f4a96cba) the test was RMS_M(e) ≤ α, eᵢ = max(0, |rᵢ|² − ρᵢ²)^½, or RMS_M(e′) ≤ α (e′ beyond max(ρᵢ, kl φᵢ)) and RMS_M(r) ≤ kg RMS_M(φ). Earlier on 2026-11-06 (maintainer: "make the relative eps h-independent"), the relative term was rstol × RMS_M(x̃ − xᵗ)/h², rstol |vᵗ/h + a|, which grew as 1/h (Trampoline.SoftSoft, first 0.3 s, medians 0.97, 1.91, 9.5 m/s² at h = 10, 5, 1 ms); rstol went from 1e-2 to 2e-2 (the soft scenes' traced pass points are the same for 1e-2 to 1e-1; 2e-2 gives the sum-of-forces form's allowance at 1e-2 where two forces balance; the paper files' 1e-2 had the former meaning). A normwise relative form, RMS_M(r) ≤ rstol RMS_M(s/m), was rejected: contact-loaded light surface nodes, whose elastic and contact forces of ~1e7 m/s² cancel, dominate its scale (DragonImpact at 7 s: 1.2e5 m/s² vs a median node's 105), so it passed the substeps' initial guesses. The force-relative form, measured when it was introduced (vs dev 814b6439): DragonImpact −24% sweeps, 3.48 vs 2.76 mm to the reference; BendingBeam.100MPa VBD −10% sweeps, 0.12 mm from dev; BasketOfFruit from step 100: no exits, bit-identical; Trampoline.SoftSoft −0.1%; CapsulesIntoBowl −1.7%. **Changed meaning (2026-10-20):** astol used to be a fraction of the scene's size L (mean body diagonal), so a hand-written astol = 1e-4 is now extremely strict (no rename, no shim). A large absolute floor hid unconverged steps (astol × L = 2.2 mm at astol = 5e-4 passed the Y = 1e8 square trampoline's ~1.5 mm residual against ~1 mm of gravity sag per step), and 1e-6 × L made runs much too slow.

  Static problems use the absolute `gtol`. `ConvergenceParams.early_exit` (default on) lets passing the tests end a solve or subproblem; off, every solve runs its full budget (fixed compute, for scenes that compare the solvers at equal work; maintainer, 2026-11-01) while the tests still run and the status records their ratios against the usual tolerances (zero tolerances, the earlier way to turn early exit off, make every ratio infinite). GPU Newton follows it too unless `Solver.Newton.early_exit` (`newton.solver.NewtonGpuParams`, `NewtonEarlyExit`: Shared, the default, follows it; Off or On override it) says otherwise. No scene config overrides it: Celebration set On while its VBD family ran fixed budgets, until every solver exited early there (maintainer, 2026-11-07). Configs with the former `rtol` are read as `rstol` (`config.RENAMED`), and `displacement_floor` is ignored with a warning (`config.DEPRECATED`). Inside a subproblem only the gradient is tested, and with the stationarity test it measures the subproblem's own residual, its augmented-Lagrangian gradient (`ConvergenceCheck.after_block`): multipliers max(0, λₖ − σc(x)) (one-sided with `vbd_slack_at_evaluation`), friction capped at μ_f times that normal force with the Coulomb limits re-evaluated at each test (unfrozen first; freezing them, GPU Newton's rule, stopped the early exits), at the subproblem's decay weights. With `multiplier_step` 1 that is what the next outer test measures after the dual update, up to its Coulomb projection and the filter (equal to the last bit on resting cubes, `TestInnerRatioMatchesOuter`). The Lagrangian at the old multipliers, tested until 2026-11-06, kept the penalty force the multipliers hadn't absorbed, so with one outer iteration it never passed. Passing ends the subproblem only: the solve is decided between subproblems, after the full dual update, the filter, the solved set's gradient, the re-detection and feasibility (`TestInnerTestEndsSubproblemOnly`). `SimulationState` builds one check and shares it among the VBD-family and Newton params (`params.convergence`). GPU Newton uses the same relative test (host-side, `ConvergenceCheck.test_gradient`/`test_feasibility`/`relative_test`): its outer test checks the Lagrangian gradient and feasibility, split around the re-detection as the VBD family's (without feasibility, a new contact's lambda = 0 leaves the free-flight guess's penetration out of the Lagrangian gradient, so the step passed before any subproblem and bodies fell through colliders), and each Newton step checks the subproblem's augmented-Lagrangian gradient, both against the step's stationarity tolerance. With `rstol = astol = 0`, or for static problems, Newton keeps its absolute `gtol2` (C++). `solve_subproblem` returns a `SubproblemStatus` (stepped, converged, non-descent, line search failed).
- Outer iterations are unrolled on the host, each inside `wp.capture_if`. Inside a subproblem, the distinct first iterations are recorded once, then a block of identical iterations replays in `wp.capture_while`. Each solver describes this with `schedule() -> IterationSchedule` (prefix, period, sweeps per iteration); AAAVBD's first iteration, Chebyshev's first two and Anderson's first m are distinct.
- Conditional graph bodies must not allocate. `ContactDetection.prepare_detection()` runs between the conditional nodes; vertex SDF's `wp.Mesh.refit` lives there, since it allocates scan temporaries. A detector without `supports_conditional_capture` (OGC, untested) keeps its whole detection and filter outside conditionals.
- At equal work, results are bit-identical to the unrolled loop, and the graph is smaller and faster.
- **Solve status.** The same kernels record each solve's outcome in a device ring, `ConvergenceCheck.status` (`SolveStatus`: solve index, outer iterations, sweeps, `SolveEnd` reason, final gradient and feasibility ratios to their tolerances, and the stationarity test's other ratios `max_ratio`, `no_floor_ratio` and `floor_clause_ratio`). `_start_kernel` advances the solve counter `solves` and starts the row; `_end_outer_kernel` updates it, counting the subproblem's sweeps from its `SweepLayout` and the blocks it ran. So recording adds no graph nodes and no synchronization. `SimulationState.step` queues an async copy of the ring into pinned memory right before its existing `wp.synchronize()` and then appends the rows to `state.status_log` (`status.StatusLog`). The ring holds one row per substep. GPU Newton is host-driven and records `NewtonSolveRecord`s (per subproblem: `SubproblemStatus`, Newton steps, max CG iterations and whether CG hit its cap, line-search backtracks; per outer test: the gradient and feasibility ratios to their tolerances, defined as the VBD family's, with feasibility measured even when the gradient test fails) from values its loop reads anyway. `simulate.py` writes each frame's statuses to `sim/<frame>/solve_status` (the steps since the previous frame; those after the last frame aren't stored) and prints a summary of every step; the GUI shows it in `panels/status.py`. Verified: VBD/AAAVBD positions bit-identical, same synchronization and kernel counts under nsys (plus one 24-byte async D2H copy per step), same graph-replay step time. Tests: `python -m unittest python.tools.sim.status python.tools.sim.panels.status`.

**Static problems.** With `fem.static` set, the objective is Ψ(x) − fextᵀx: solvers drop the inertia term, use `fem.h2 = 1` instead of `BetaTilde²`, and Newton SPD-corrects d²Ψ/dF² in every problem (`gpu/elasticity/spd.py`, mode `Solver.Newton.spd_correction`, C++ default Absolute). Its CG limits are `newton.solver.LinearSolverParams`.

**How solver names map between GPU and CPU:**
- `VbdSolver` is plain VBD.
- `AaaVbdSolver` adds per-vertex *stencil gradient acceleration* (`betaG`, `rhohat`, `gammaup`/`gammadown`, separate interior/surface values in `vec2f`). In C++ this acceleration is built into `vbd::Iterate` itself.
  - Prefer one shared set of AAAVBD's own parameters across scenes: the Lipschitz normalization is meant to make them problem-invariant, a selling point of the method. Tune budgets, convergence thresholds and contact first; change an AAAVBD parameter for a scene only if necessary, and note why.
  - Only AAAVBD reads the stencil parameters, so `gpu/vbd/params.py::STENCIL_GRADIENT_ACCELERATION_KEYS` lists them once: they are serialized (and so appear in configs) and shown in the GUI for AAAVBD only, and ignored when an older file stores them for VBD, Chebyshev or Anderson.
  - `warm_start_beta` follows C++ `InitializeSolve`/`PrepareSubproblem`: `initialize_solve` and `prepare_subproblem` reset `betaG` to `betaG0` with a capture-safe fill (0 `Never`: every subproblem; 1 `Subproblem`: every time step; 2 `TimeStep`: never). The GPU default is 2 (`SimulationState.__init__`), unlike C++'s 1, so that betaG warm starts across time steps.
  - `surface_stencil_surface_neighbours_only` (default 1, as in C++): surface vertices sum only their surface neighbours' gradients in the stencil augmentation; 0 makes them use interior neighbours too. Interior vertices always use all neighbours.
  - GPU-only ablation parameters, in `gpu/vbd/params.py::AaaVbdCpuParams`: the C++ `vbd::Params` rejects new attributes, so AAAVBD's CPU params wrap it (`vbd_params`, drawn as a GUI sub-tree) and forward every other attribute to it. `betaup` (default 1, both groups) is the limit betaG grows toward, `betaG += (betaup - betaG) gammaup`; above 1, betaG can exceed 1. `lipschitz_normalization` (default 1) divides rho by the vertex Lipschitz estimate `L = |H_i|_F + |g_k| / |x_k - x_k-1|`; with 0, `rho = |g_k - g_k-1| / |x_k - x_k-1|`, so `rhohat`/`rhohatS` have stiffness units and their values aren't comparable. C++ keeps the hard-coded 1 and always normalizes, which the defaults reproduce bit-identically.
- Chebyshev and Anderson wrap the VBD sweep, matching C++ `Chebyshev.h` and `Anderson.h`. The GPU Anderson solves its least-squares problem by normal equations or CG (`AndersonLinearSolver`), whereas the CPU version uses a COD.
- `NewtonSolver` assembles the sparse Hessian from triplets and has `supports_graph_capture == False`. It starts each time step from its own initial guess, `Solver.Newton.init_strategy` (`newton.solver.NewtonGpuParams`, default Position, i.e. x_t; maintainer), instead of the shared `Integration.init_strategy` that the VBD family uses (`SimulationState.step_init_strategy`): an extrapolated guess can start deep inside a contact partner at an impact, where Newton's first linearization is poor (it went unstable at the sphere's impact on the soft-stiff trampoline). The benchmark doesn't use either: dynamic problems give every solver the file's x0. `Solver.Newton.one_sided_contact` (GPU only, default off as C++) eliminates the contact slack from its augmented normal terms, E = (max(0, λ − σg)² − λ²)/(2σ) for the gap past the margin g, so a contact pushes only while pressed and has no Hessian block otherwise; with the slack fixed per Newton step, an unpressed contact in the detection band is a stiff two-sided spring, which kept Celebration's confetti on vertical letter faces with friction off (2026-11-01). Its Armijo test tolerates energy increases within float32 roundoff, `8 eps h^2 sum_e w_e mu_e` (`Params._energy_roundoff`): Stable Neo-Hookean's Psi(F) loses precision near rest (I_C - 3, J - 1), so near convergence the predicted decrease falls below what float32 resolves, and the steps would fail on noise. C++ rejects those steps.

**Kernel conventions.**
- **Thread layout.** The vertex solves launch `dim = n_verts_in_partition * 32` with `block_dim = 32`. Each block handles one vertex: threads stride over its adjacent elements and contacts, the partial sums are reduced with `wp.tile` + `wp.tile_reduce`/`wp.tile_sum`, and thread 0 does the 3x3 solve and writes `fem.x[i]`.
- **Vertex solve singularity check.** `hess_zero` is relative to the scale of the vertex Hessian, unlike C++, where it is absolute (`kernels.integrate_positions`). Inverse skips the vertex when `|det H| <= hess_zero (|H|_F/sqrt(3))^3` (robust to indefinite H), and EVD zeroes eigen-components with `|lambda| <= hess_zero max|lambda|`. QR has no check. An absolute threshold on `det H ~ m^3` froze light vertices at small time steps (`H ~ m I`): at h = 1e-4, 618 of the trampoline's 5957 free vertices never moved. The C++ binding's tooltip still says "Determinant of Hessian zero threshold".
- **Gauss-Seidel ordering.** Color partitions run sequentially from the host (`params.Pptr` stays on the CPU; `Padj` is on the device).
- **Contact lagging.** `params.xb` is a snapshot of `x` taken before each sweep and is used to evaluate contacts.
- **Precision.** Everything is `float32` (`wp.vec3f`, `wp.mat33f`). The custom matrix and vector types are in `gpu/types.py`.
- **Ported math.** `gpu/elasticity/snh.py` (Stable Neo-Hookean) and `gpu/elasticity/chain.py` (∂Ψ/∂F → ∂/∂x) are direct ports of `physics/StableNeoHookeanEnergy.h` and `fem/DeformationGradient.h`.

**Small dense linear algebra inside the solver** (e.g. the Anderson least-squares step in `gpu/vbd/aasolver.py`):
- **Use Warp tile ops.** `wp.tile_matmul`, `wp.tile_cholesky`, `wp.tile_cholesky_solve` and `tile_*_solve` are backed by MathDx and capture cleanly.
- **Avoid CuPy's cuBLAS and cuSOLVER.** CuPy raises `NotImplementedError` for any cuBLAS or cuSOLVER call during stream capture, even through its low-level `cupy_backends` bindings.
- **Kernels with shape-specialized tiles.** Kernels whose tile shapes depend on a parameter (e.g. the Anderson window `m`) are generated per value with `module="unique"`. They must be created before capture starts (`AndersonParams` builds them in its constructor), so that capture's module force-load includes them.
- **Anderson solve modes.**
  - The Gram matrix of `[F f]` comes from one tiled pass. `FfT` stores `F^T` and `f` as one `(m+1, 3N)` buffer. Each tile writes its product to its own row of `Gp`, and a second kernel sums the rows in a fixed order, so Anderson runs are bit-reproducible (an atomic accumulation's run-to-run rounding noise changed the iterates near the float32 floor). The second kernel costs about 2 µs (~2%) per Anderson iteration on the trampoline.
  - It is then solved by Cholesky, which regularizes only when a pivot falls below the relative threshold `cod_numerical_zero`, or by unregularized Jacobi-PCG.
  - `vbd_iters_per_anderson_iter` (`p`, GPU only) makes each Anderson iteration apply `p` VBD sweeps. `n_subproblem_max_iters` still counts sweeps, as for every VBD-family solver: a subproblem runs `n // p` Anderson iterations, then the `n % p` leftover sweeps as plain VBD sweeps (`aasolver.sweep_budget`, `IterationSchedule.tail`).
  - Tests: `python -m unittest python.tools.sim.gpu.vbd.aasolver`.
  - `docs/anderson-implementation-notes.md` records the pitfalls behind these choices (relative regularization, deterministic Gram, the float32 floor), with evidence, for the paper. Add an entry when a new one comes up.

**CUDA graph capture.** `state.SimulationState.step` records one `wp.ScopedCapture` of `substeps × (setup → solve → step)` and replays it. Capturing doesn't execute anything, so the first step launches the graph right after recording it. That means `solve()` on a capturable solver must:
- not allocate,
- not copy device data back to the host,
- not use Python control flow that depends on device values.

Loop counts come from host-side params, so changing them requires a recapture. The UI sets `state.capture = None` on reset. Handles must stay stable across steps, which is why `cd.register_handles(...)` is called once and buffers are preallocated with capacity multipliers (`gpu.contact.mesh.pairs.Params`). Work that is independent across contact types runs on separate `wp.Stream`s, one per VV/VE/VF/EE.

## Kinematic constraints

`gpu/kinematics/constraints.py` (module docstring has the exact semantics) mirrors the CPU editor's `TransformLibrary.evaluate` (`python/tools/vbd/ui/utils/transform_library.py`):

- **Data.** A `KinematicConstraint` prescribes the motion of a node group (`Fixed`, `Translate`, `Rotate`, `RadialTranslate`) over a half-open time window `[begin, begin + duration)`, rounded to the step grid. A `KinematicConstraintSet` holds all of them on the device.
- **Evaluation.** Positions are evaluated in closed form from per-node anchors (the position when a node's constrained run starts), composing overlapping constraints in order, so nothing drifts. Constrained nodes get the analytic prescribed velocity, so they keep moving when released.
- **Ownership of `dmask`.** `FemElastoDynamics.setup_time_integration_optimization` calls `kinematics.update(...)` first, which rewrites `dmask` and sets `x`/`v` of constrained nodes. Their `xtilde` is then their end-of-step position. `fem.step()` advances the device step counter. Time therefore lives in a device array and replays correctly in the captured graph. `advance_time = False` freezes it (needs a recapture).
- **Loading.** `state.load_kinematic_constraints` reads the Dump's `kinematics` group (written by `TransformLibrary.export_kinematic_constraints`, including `t0` and the anchors of runs open at Dump time). Dumps without one treat nonzero `dmask` as permanently fixed. `SimulationState` attaches a fresh set to every GPU FEM (construction and `reset`).
- **Contact.** `ContactDetection.register_handles(..., dmask)` makes `filter_step` skip constrained nodes, like C++ `RestoreFeasibility(x, dmask)`.
- **GUI.** `panels/kinematics.py` lists, toggles (on the device, no recapture) and highlights constraints.
- **Tests.** `python -m unittest python.tools.sim.gpu.kinematics.constraints` checks the GPU against the CPU editor, graph replay, releases and anchors.

## Contact on the GPU

The GPU uses the same contact model family as C++ `MeshDynamics`: an augmented Lagrangian with slack `s`, multipliers `lambda_n`/`lambda_f`, a decay weight `gamma`, and Coulomb friction in a 2D tangent basis. The code is organized differently from the C++ side, though:

- **`contact/mesh/cd.py`.** The abstract `ContactDetection` is pluggable, with implementations `ogc.Ogc` (Offset Geometric Contact, with BVHs over edges and faces) and `sd.Sd` (vertex vs. `wp.Mesh` SDF). The UI defaults to `VertexSdf`. Its `detect_contacts` postcondition requires pairs to be unique and sorted by `v` per `u`, followed by a call to `contacts.assemble_contacts()`. `filter_step` modifies `x` to keep steps feasible, which is the GPU analogue of `RestoreFeasibility`. Vertex SDF detects a vertex closer than `Contact.ContactDynamics.dmin + Contact.CDType.VertexSdf.band` to another mesh (or inside it), as C++ OGC detects within a radius above the margin. The AL pushes resting contacts to `dmin` outside, so a detection band below `dmin` would drop them every step and lose their multipliers (penetration-only detection, the old `VertexSdf.dmin = -1e-4`, did exactly that; configs with that key get a deprecation warning). A time step's first detection (`initialize_solve`, `from_xt`) is at xt, as C++ `vbd::InitializeSolve`, and also detects the pairs that the step's starting iterate x0 (the init strategy's predictor; xt for Newton's Position) or its inertial target xtilde may bring within the threshold: from the vertex's motion x0 - xt (and xtilde - xt) relative to its xt closest point, delta, it accepts sd - |delta| below the threshold on meshes and the exact sd + n . delta on planes (motion along a plane doesn't widen), the smaller of the two gaps, with each query reaching the threshold plus the vertex's and its partner's largest motion to either. The xtilde term matters for Newton's Position start, which x0 alone doesn't widen at all: Celebration's confetti 13 mm apart at xt (threshold 8 mm) and closing at ~19 mm per step had no contact in the first subproblem and went 17 mm through each other, a tangle (step-91 replay, step-end feasibility 6.5-7 over 3 steps; with it 0.17-0.47 over 5 steps, 2026-11-07). On CapsulesIntoBowl Newton resumed at step 300 (the pile) it requested at most 11/302/3951 VV/VE/VF pairs, about what AAAVBD requests there (11/300/3947), within the capacities (5146/15137/30274). C++ widens its OGC query radius, within which it creates contacts, by max |xtilde - xt| in both `vbd::InitializeSolve` and `newton::InitializeSolve`. For the VBD family's default start (TrajectoryWithExternalLoad, x0 = xtilde bit for bit) it changes nothing (CapsulesIntoBowl AAAVBD from step 300, 11 steps under graph capture: positions bit-identical to dev 93cce4f4); static problems (no inertia) aren't widened by xtilde (`ContactDetection.on_time_step_started(widen_by_inertial_target=not fem.static)`); the step filter's distances stay those at x0. Detection at the predictor (until 2026-10-22) started fast bodies deep inside thin partners (ArmadilloSpaghetti.Fall diverged at step 60; CubeFallingOnCube's top cube fell through); a global widening by the fastest body's motion overflowed CapsulesIntoBowl's VE capacity. Vertex SDF's normals point from the partner surface to the vertex on both sides: the face normal for VF, and for VE and VV the closest-point direction, signed by the detection's own inside/outside test on closed partners (Warp's ray vote, which also signs the distance that detected the pair) and by the edge or vertex pseudonormal on open ones. The pseudonormal's sign is exact only on an embedded surface: where an impact inverts a surface tet, its two exposed faces fold over each other, their normals nearly cancel at the fold edge, and outside vertices over that edge got normals into the partner, a false penetration of |d| + dmin (DragonImpact, docs/solver-accuracy-notes.md entry 8; test in `sd.py`). The feature (VF, VE or VV) comes from exact zeros of the closest point's region barycentrics (`queries.closest_point_triangle`, as C++ OGC's `UvwPointInTriangle` and the VF second pass in `pairs.py`), so VF means strictly inside the face. Warp's mesh-query barycentrics aren't exact zeros (w = 1 - u - v is ~1e-8 on a face's edge jk): classified by them, edge contacts stayed VF with the face normal, a false penetration behind sharp edges (the armadillo's thin features, 2026-10-22; test in `sd.py`).
- **Frozen linearizations within a solve** (`Contact.CDType.VertexSdf.freeze_within_solve`, `sd.py`; on by default since 2026-11-06, maintainer; off reproduces the earlier detection bit-identically, BasketOfFruit AAAVBD under graph capture vs dev 3075b266). Each detection linearizes a contact at the current positions (feature, barycentrics, basis), so re-detecting after every outer iteration changes the constraints the AL solves for. On ArmadilloSpaghetti.DragonImpact that put the outer loop in a period-2 cycle: ~1,100-1,750 pillar contacts flipped feature (VF <-> VE, neighbouring faces) at every re-detection, the iterate alternated by ~20 um (tolerance 4.9 um), and it drove entry 13's multiplier zeroing (docs/solver-accuracy-notes.md). With the option, the solve's first detection (from xt) is full; at each later one, a (surface vertex, other mesh) pair that the previous detection has keeps its feature, barycentrics and basis while its stored linearized gap n . (x_i - c) at x stays below the threshold `dmin + band` (and, on plate colliders, above their depth): its key is emitted without a query and `_restore_kept_stencils` puts its stored stencil back after `assemble_contacts`. A pair whose gap leaves the threshold is detected afresh (dropped, or a new feature), and pairs new to the band are added. The working set is a capture-safe copy of the last detection's forward VV/VE/VF pairs (allocated only with the option). **The solve's last detection is full**, so the next solve warm-starts from keys detected at its xt and a budget of 1 outer iteration equals the default: the VBD family passes `fresh` to the last scheduled re-detection, and since an early exit is decided on the device, `solve_outer_loop` adds a `wp.capture_if(cd.last_detection_frozen)` after the outer loop that re-detects fully and updates the constraint set (the flag is set by a frozen detection and cleared by a full one; the BVHs were refit at the final positions by the last `prepare_detection`). After an early exit the status's feasibility was measured on the frozen set that decided the stop. GPU Newton does the same on the host (`NewtonSolver.solve`). OGC ignores the option (every OGC detection is full). Measured off -> on (2026-11-06, the same numbers as the `investigate/stable-contact-set` prototype): DragonImpact AAAVBD 10 x 100 from 7 s, motion per outer iteration at the last re-detection 19.9 -> 0.67 um (first 25.7), multiplier zeroings per update 223 -> 3, feature changes 1378 -> 0, solved-set ratio 12.0 -> 10.3, ratio on a fresh detection 1054 -> 696, fresh-detection penetration 0.18 -> 0.12; BasketOfFruit production 5 x (3 x 50) from step 50, 10 steps: AAAVBD median/p90/max outer ratio 471/943/1401 -> 407/878/1283, VBD 391/437/503 -> 390/452/509, end-of-solve feasibility medians 0.20 -> 0.40 (AAAVBD) and 0.29 -> 0.60 (VBD, max 1.19 -> 1.44; the frozen planes let vertices drift into the margin, never across it), step time -1% (fewer queries: kept pairs skip theirs). GPU Newton on Celebration (10 x 2 from 0.5 s, 3 steps, one run each, Newton isn't reproducible): the per-outer ratio's period-2 cycle (entry 16) became monotone (step 52: 129, 24, 579, 1669, 178, ... -> 147, 42, 25, 17.6, 17.8, ...); end ratios 17.5/18.3/17.8 -> 16.2/49.0/17.8 (step 51 settled on its frozen set at 49), step time about equal. Rejected variants (freeze without drop, hysteresis, dropping pairs at lambda_n = 0) are noted at the option. Tests: `TestFreezeWithinSolve`, `TestFreezeLastDetection` in `sd.py`, `TestFreezeWithinSolve` in `newton/solver.py`.
- **`contact/mesh/pairs.py`.** `ContactPairs` stores forward and reverse VV/VE/VF/EE pairs plus per-contact bases. Reverse pairs let a vertex solve gather the contacts in which it's the edge or face side.
- **`contact/constraints.py`.** `ConstraintSet` holds per-type dual state (s, gamma, the dual update's pending gamma `gamma_next`, lambda_n, lambda_f, and GPU Newton's frozen Coulomb limit `friction_limit`) and warm-starts it across constraint-set updates: each update records every contact's key (u, v), and pairs found again keep their state, as C++ `DenseAdjacencySet::Assign`. **Feature transitions** (GPU only, `constraints.carry_across_features`, run by `MeshDynamics.update_constraint_set` after the exact-key warm start): a new VV/VE/VF contact without an exact previous key inherits the slack, gamma and multipliers of a previous contact of the same vertex whose partner feature shares a mesh vertex with its own (face, edge or vertex in the closed one-ring; no normal test), one-to-one and never summed (mutual first choices: the new contact prefers the largest previous lambda_n, the previous one VF, VE, VV in slot order; exact keys win). lambda_f is re-expressed through 3D into the new tangent basis, from the previous update's bases (`ConstraintSet.tangent`/`bitangent`, checkpointed); GPU Newton's frozen Coulomb limit doesn't carry. Why: sliding capsule vertices on CapsulesIntoBowl change features at ~3% of their contacts per detection, 2/3 of them to a neighbouring face, and ~2% of contacts ended each step pressed with lambda_n = 0, which made the outer test's residual floor (docs/solver-accuracy-notes.md section 4). Edge-edge contacts (OGC) keep exact keys only (TODO in constraints.py). Other new pairs start at lambda = 0, gamma = 1 and s = 0. The solvers refresh the slack s = max(0, c_n - lambda_n / sigma_n) from the positions before using it, as C++: the VBD family before every sweep, GPU Newton before every Newton step's gradient (`newton.solver._subproblem_gradient`, as C++ `ToGradient(..., bForSubproblem = true)`), and it is then fixed for the step's Hessian and line-search energies. GPU Newton used to refresh it only in `finalize_subproblem`, so each subproblem ran on the previous one's slack and contacts detected since then on their slot's previous contact's: per-vertex pushes and pulls (jagged interfaces on soft-on-stiff contact, 2026-10-21) and spurious decay of pressed contacts. On the soft-stiff trampoline + sphere the refresh cut the contact region's roughness 2x (still ~2x AAAVBD's; idea: TODO in newton/solver.py) and the worst feasibility ratio from 9.9 to 0.002. Persistent multipliers need a penalty near the vertex stiffness: with a soft one, lambda integrates over a deep penetration and the slack lets it push until the gap reaches lambda / sigma, which ejects resting bodies (as in C++, whose penalty is always adaptive).
- **`contact/dynamics.py`.** `MeshDynamics` handles dual updates and adaptive penalties. GPU-only differences from C++:
  - `PenaltyAdaptivity` (CONSTANT/TIMESTEP/SUBPROBLEM). CONSTANT: `sigma_n = sigma_f = dt^2`, so `gamman * dt^2` and `gammaf * dt^2` are stiffnesses scaled like `dt^2 Psi` (1e4 * 1e-4 = 1 by default). TIMESTEP/SUBPROBLEM: `sigma_n = sigma_f` = the global max contact Rayleigh quotient of the vertex Hessians, per time step or per subproblem, scaled by the dimensionless `gamman_adaptive`/`gammaf_adaptive`. The default is TIMESTEP with `gamman_adaptive = 1`, C++'s value: with warm-started multipliers, softer penalties (CONSTANT at `gamman = 1e4`, or `gamman_adaptive = 0.1`) eject resting bodies, while at 1 every VBD-family solver keeps the plane scenes and BeamFallingOnBeam finite and at rest on the margin. In these modes the VBD vertex solves read contact partners of other colors at their current positions (same-color ones stay at the sweep snapshot `params.xb`), because lagged partners diverge once the penalty reaches the vertex stiffness. C++ lags all of them.
  - `penalty_stiffness` (C++ `ePenaltyStiffness`, typed `pbat.sim.algorithm.vbd.SALPenaltyStiffness`): GlobalMaxRayleighQuotient (default) or LocalMaxRayleighQuotient, each contact's own floored quotient `Qc` (the global penalty is their max), recomputed for the new slots at every constraint-set update from the last adaptation's Hessian (GPU Newton keeps a copy of its contact-free H); ignored with CONSTANT.
  - GPU Newton adapts the penalties from its assembled Hessian without contact terms, as C++ `UpdatePenaltyParameter(H)`: each contact's Rayleigh quotient grad c^T H grad c / |grad c|^2 sums over the stencil's 3x3 BSR blocks, off-diagonal ones included (`MeshDynamics.adapt_penalty_parameters_to_hessian`; Dirichlet nodes' blocks are skipped, as C++'s static nodes aren't in H). The VBD family uses the vertex Hessians, i.e. the diagonal blocks. TIMESTEP adapts in `initialize_solve` and SUBPROBLEM in `prepare_subproblem`, as for the VBD family.
  - `min_sigma_n` (N/m, default 1e4) floors the effective normal penalty in both adaptive modes at `h2 * min_sigma_n`, h2 the solve's `FemElastoDynamics.h2` (BetaTilde² of the substep, 1 for static problems), like the stiffness part of the vertex Hessians: exactly 1 at 10 ms without substeps (a float32 product, `MeshDynamics.penalty_floor`), 0.01 at 1 ms. **Changed meaning (2026-10-26):** it was a fixed floor of 1, the value the paper configs carry; the scene configs set 1e4 (`scene_configs.PENALTY_FLOOR`).
  - Friction: the dual update projects `lambda_f` onto the Coulomb cone. The VBD vertex solves (`kernels._contact_derivatives`) also cap the primal friction force `sigma_f c_f - lambda_f` at `mu_f` times the contact's current normal force `max(lambda_n - sigma_n c_n, 0)`, and scale its Hessian block by the same factor. C++ has no such cap: without it, the friction penalty acts as viscous drag within a step, even at `mu_f = 0`. The lagged multiplier `lambda_n` alone can't serve as the limit: it's ~0 on resting and sliding contacts. GPU Newton caps friction consistently with its line search, at a limit C = `mu_f max(lambda_n - sigma_n c_n, 0)` frozen per contact for the time step (first come, first served; maintainer, 2026-10-20): each contact's first strictly positive estimate in the step, at an augmented gradient evaluation (`gpu/gradient.py`, `contact.constraints.frozen_friction_limit`), sets its C, so contacts pressed at the step's first detection get it from the step's first normal-force estimate and the others from their first positive estimate, and every later outer iteration and Newton step of the step, Hessian and line-search energies included, uses that C. It's stored next to the multipliers (`ConstraintSet.friction_limit`) and carried across re-detection by the same (u, v) warm start, so a contact dropped by one detection and found by a later one starts over, like its multipliers; Newton's `initialize_solve` unfreezes every limit (`MeshDynamics.reset_friction_limits`, a memset per contact type). While a contact's estimate is 0 (detected inside the band but not yet pressed: lambda_n = 0, c_n >= 0, e.g. an impact first detected at x_t), C is recomputed at each evaluation and not stored, so the contact gets friction once it carries load, within the same step (maintainer, 2026-10-21; freezing the first estimate, even 0, left such impacts frictionless for their whole first step). Only the augmented gradient writes C, and it runs only at accepted iterates (each subproblem's start and after each accepted step), before the Hessian and line-search energies that read it; those read an unset limit as 0 (`contact.constraints.stored_friction_limit`), the gradient's own value there. Reading the -1 marker as a limit gave the Hessian a friction scale -1/|f| (-inf at f = 0, e.g. a new contact at x_t: NaN blocks, every CG at its cap) and the energy a -|f| / sigma_f term, so line searches failed at the sphere's second contact frame. Test: `python -m python.tools.sim.gpu.contact.dynamics` (energy slope vs gradient, Hessian scale in [0, 1], set and unset limits). Why: re-evaluating C at every Newton step made it, and the friction energy, jump between outer iterations where sigma_n is adapted to a stiff partner, since tiny gap changes move sigma_n c_n a lot: the sphere's contact patch on the soft-stiff trampoline's Y = 1e8 center was unstable with friction and stable without (lowering `gammaf_adaptive` 10x didn't help). The VBD family's vertex-solve cap is unchanged (its per-vertex evaluations of a contact happen at different positions in different colors, so a first-evaluation freeze would depend on the sweep order). The friction energy is Huber-like, unchanged for |f| <= C and continued linearly above (C^1, `contact.dynamics.capped_friction_energy`), so energy and gradient agree within the step; the Hessian's friction block is scaled by min(1, C/|f|). The Lagrangian gradient (outer test) is uncapped. Capping only the gradient and Hessian while the line search kept the uncapped energy made most steps fail Armijo, and without any cap Newton stuck at every `mu_f` and failed its outer test (the dual update clips `lambda_f` to the cone while the penalty holds the body). Incline (CapsulesIntoBowl's contact settings, Newton 10 x 2), measured with the per-step freeze (2026-10-22): 0.52 m/s^2 from rest and 0.67 sliding from 3 m/s at `mu_f = 0.2` (Coulomb 0.64), sticking at 0.3, an impact friction ratio of 1.25 (AAAVBD 1.01), no line-search failures, outer test passed on 147 of 150 steps. The per-step freeze is kept on purpose (maintainer: Newton should over-estimate the normal force); the alternatives tried (the outer iteration's lambda_n, a per-subproblem re-freeze) and why they lost: docs/solver-accuracy-notes.md, entry 6. C++ has no cap. With the cap and persistent multipliers, the defaults `gammaf = 1e3` and `gammaf_adaptive = 1e-2` reproduce Coulomb sliding and sticking on the inclined-plane test. See the sim-run skill's "Tuning".
  - The penalty starts at `dt^2`.
  - Decay (`_apply_dual_update`): at each full dual update a pressed contact's gamma resets to 1 and every unpressed one decays by `decay`. C++ decays only on slack growth since the last sweep, close to chance on BasketOfFruit. With `vbd_slack_at_evaluation`, decaying every unpressed contact gave a lower median, p90 and max outer residual than that rule in all four BasketOfFruit segments measured (AAAVBD 1 x 80 and VBD 3 x 50 at steps 50 and 100); on Trampoline.SoftSoft the totals were lower and the worst step 10% higher with early exit off, accepted by the maintainer (2026-11-05). A rule decaying only contacts predicted to separate (gap plus the substep's normal motion past `dmin`) was more accurate but raised the residual: the unpressed contacts it kept at gamma = 1 held their vertices with full-strength Hessian blocks. The decided weight is pending until after the outer test (see "Convergence and early exit").
  - `vbd_slack_at_evaluation` (default 1 since 2026-11-05, maintainer; VBD family only; Newton's counterpart is `Solver.Newton.one_sided_contact`): on, the vertex solves evaluate the slack at each evaluation's own gap, so the normal force is the one-sided gamma max(0, lambda_n - sigma_n g) (none from unpressed contacts) while every contact keeps its Hessian block gamma sigma_n n n^T as a proximal term; the friction cap uses the same force. Off, the slack refreshed before the sweep makes an unpressed contact a spring toward its sweep-start gap. Test: `python -m unittest python.tools.sim.gpu.vbd.kernels`.
- **Choosing contact parameters for a scene.**
  - Keep the adaptive penalty (TIMESTEP, the default); use SUBPROBLEM only when it clearly helps a scene, and CONSTANT only with a stated justification. Soft constant penalties let resting bodies sink or eject with persistent multipliers and give deep impact penetration.
  - Use a small positive margin `Contact.ContactDynamics.dmin` (a few mm). Negative margins are a leftover of penetration-only detection: resting vertices then sit inside their partner, where the SDF sign is least reliable.
  - Keep `Contact.CDType.VertexSdf.band` small, close to `dmin` (e.g. 2 mm with `dmin = 1 mm`; maintainer), and scale `max_dist` to the geometry. The band must keep resting contacts detected and catch what can reach a partner within a step, but a band much wider than the margin holds separating bodies together: with a 2 cm band, the sphere stuck to the square trampolines under Newton. Too small a band (the 1 mm default on ~10 cm thick plates) misses contacts, lets vertices reach a thin body's far side, and their contacts then pull bodies through, so check thin plates for pass-through after narrowing it. Fast impacts can need a little more: the sphere falling on the trampolines exploded at 2 mm on the heterogeneous circle trampoline, and at 5 mm on the second bounce without substeps; it uses 1 cm with max_dist 50 cm (maintainer). The Solve status panel's feasibility ratio shows remaining penetration.
- **`contact/debug/contact.py`.** Polyscope browsers for inspecting individual contact stencils.

## Params, UI and serialization

- **Configs.** Parameter files are layered TOML (`configs/README.md`, `config.py`). Their tables mirror the HDF5 groups that `serialize_params` writes. `--sim-params` merges `.toml`/`.h5` sources left to right, then `--set Table.key=value` overrides. Unknown and missing keys raise `ConfigWarning`, checked against what the code serializes, so a new serialized parameter is picked up automatically. `configs/paper/*.toml` are the paper's hand-tuned files: never edit them, `extends` them instead; they are regenerated only by `python -m python.tools.sim.paper_configs make` (which also regenerates `configs/defaults.toml`; `check` verifies them). They aren't authoritative tunings: check a paper file's budgets and vertex solve against the tuning guidance (sim-run skill). `configs/scenes/*.toml` (one per paper scene) are complete parameter sets generated from the paper configs and the maintainer's rules by the temporary `python -m python.tools.sim.scene_configs make` (`check` verifies them): change a scene's settings in its `SCENES` table, not in the file. Configs are TOML; data (trajectories, datasets, meshes) is HDF5. Prefer scene files (`--scene`) plus `--sim-params` as inputs; Dumps are for reproducing a mid-simulation state, e.g. a crash.

- **Serialized but ignored on the GPU** (a documented gap, by the maintainer's choice; `python -m python.tools.sim.config params` annotates them): Rayleigh damping `betaR` of the VBD-family solvers (copied to the GPU params, but no kernel reads it, so a config's damping does nothing here, unlike C++), `e_penalty_stiffness` (the GPU contact penalty comes from `Contact.ContactDynamics.penalty_adaptivity`), and `Solver.Newton.linear_solver` (the GPU Newton always uses Warp's Jacobi-preconditioned CG, set by `Solver.Newton.LinearSolver`).

- **GPU-only parameter classes** use `common.fields.DocField` descriptors (a default value plus a docstring that becomes the imgui tooltip) together with `SerializableMixin`, which serializes them to h5 attributes.
- **UI widgets.** `panels.common.draw_params` reflects over objects: every public, settable `float`/`int`/`bool`/`Enum` attribute gets a widget. So a new C++ `Params` field bound with `def_rw`, or a new `DocField`, appears in the UI without any UI code.
- **CPU param serialization.** CPU param objects are serialized by the same reflection (`serialize_vbd_cpu_params`, etc. in `gpu/vbd/params.py`). The group layout (`Solver/<SolverType.name>`, `Contact/...`, `Integration`) is defined in `state.serialize_params`/`deserialize_params`.
- **GPU mirror updates are manual.** A field that kernels need must be copied into the `*Data` struct in the GPU `Params.__init__`. A new solver also has to be registered in `state.py` (`SolverType`, both `SimulationState.__init__` and `reset()`, `serialize_params`/`deserialize_params`) and in `ui.py` (`SOLVER_SUB_PARAMS`).

## Profiling

- **Scopes.** `gpu/common/profiling.py` provides `with profiling.scope("vbd.sweep"):`, the `@profiling.scoped("name")` decorator, and `push`/`pop` for inline regions (Newton's loop). Names are dotted and nest at run time into paths such as `solve/solve.finalize_subproblem/contact.detect`. Every GPU activity is attributed to the innermost scope open at its launch. With the backend `OFF` (the default), scopes are no-ops and safe inside graph capture.
- **Execution.** Any other backend makes `SimulationState.step` run eagerly, since per-kernel timing needs eager launches. `simulate.py --profile-warmup N` runs the first N steps unprofiled, with graph capture, then switches profiling on.
- **Nsight Systems is the reference.** `python -m python.tools.sim.profiling.nsys run -o out/prefix -- <simulate.py args>` runs `simulate.py --profile nvtx` under nsys, limits the capture to the measured steps, and imports the trace into `out/prefix.json`. Every kernel is included (Warp, CUB, cupy) with true GPU durations. nsys hangs on the venv's `python.exe` launcher, so the runner launches the base interpreter through `profiling/venvrun.py`. The nsys and ncu runners locate the executables at run time (`profiling/nsight.py::find_tool`: `--nsys`/`--ncu`, `NSYS`/`NCU`, `PATH`, then the standard install locations).
- **Kernels backend (in-process, CUPTI).** `--profile kernels` times every kernel, memset and memcpy with CUPTI (`gpu/common/cupti.py`, a ctypes binding to the DLL from the pinned `nvidia-cuda-cupti-cu12` wheel; `cupti-python` has no Windows wheels). It attributes each activity to its scope through CUPTI external correlation ids. Don't use Warp's activity timing (`wp.timing_begin`) for this: in eager mode each measurement includes launch latency, which inflated totals about 4× on the beam. CUPTI and nsys can't run in the same process.
- **Production timing.** `simulate.py --profile-out f.json` with profiling off records each step's GPU time from CUDA events around the step (graph replay for capturable solvers).
- **GUI panel.** `panels/profiling.py` ("Profiling" tree node) toggles the CUPTI backend and shows a rolling window of GPU busy time by phase, by scope path, or as a scope tree with total (inclusive) and self columns. Export writes JSON for the report. `ui.py` wraps `state.step()` in `profile_step(state)`.
- **Report.** `python -m python.tools.sim.profiling.report a.json b.json ... -o report.html [--slices 10,90]` takes one profile per solver and any production runs. It writes stacked bars, donuts, tables and a per-solver scope tree with total and self times, plus per-step statistics (`profiling/step_stats.py`): quantiles of the step and phase times, the phases over the run, and the steps grouped by percentiles of their GPU time and of their peak node speed, with a phase donut, early exits, iterations and residual ratios per group. Phase charts use each phase's union over streams (`union_ms`), so concurrent streams count once; they exclude graph launch overhead and the gaps between kernels, which only production runs include.
- **Per-step solver data.** `simulate.py` adds each profiled step's solve statuses to its profile entry (`status`, `status.StatusLog.step_entry`: outcome, iterations, residual ratios per substep), in every mode. `python -m python.tools.sim.profiling.trajectory profile.json out.h5` adds `peak_speed`, the largest node displacement between consecutive saved frames over their time interval, and `rms_speed`, the free nodes' mass-weighted RMS speed sqrt(2K/M) over it (Dirichlet nodes, static or kinematic, left out), from the run's output (frames carry their step count, `sim/<frame>.attrs["t"]`); run with `--fps` at the step rate for one value per step. Neither touches the solvers or the step loop.
- **Paper figures.** `python -m python.tools.sim.profiling.paper_figures <kind> results.json ... [--production p.json ...] -o prefix` writes the paper's PDFs (the benchmark figures' conventions: Biolinum, printed `--width`, one legend on top, no titles) and LaTeX tables; kernels and production results are paired by scene and solver. Phases are grouped by its `PHASE_GROUPS` (scope → group, fixed colors: muted olive, khaki, slate and brown tones that share no hue with a solver color, so phase fills never read as solver lines). The module docstring has every kind; the paper's:
  - `timeline`: a kernels run's phase groups per step over simulated time (groups under 3% of the GPU time fold into a top Other band, with a legend entry only if it reaches 3% itself; say what it holds in the caption), with the step times of the scene's production runs (its own solver's and others', e.g. VBD over AAAVBD's phases) in solver colors, and below them one strip of the production runs' per-step stationarity test ratios (`status_ratio.stationarity_test_ratio`: max(`gradient_ratio`, min(`no_floor_ratio`, `floor_clause_ratio`)), at most 1 iff the test passed, whereas `gradient_ratio` alone can be below 1 on a step that failed the floor clause; runs recorded before those fields existed, and GPU Newton, plot `gradient_ratio`; log, rolling median of `--smooth` steps, no raw per-step curves, dashed line at 1) over the RMS speed `rms_speed` (right axis: the paired run's as a light fill; `--rms-speed all` adds the other runs' as dotted lines, one legend entry each; run production with `--fps` at the step rate and annotate it with `profiling.trajectory`); `--snapshots TIME=IMAGE ...` adds a numbered snapshot row, marked on the plots. `profiling/snapshots.py` renders the snapshots with Polyscope from the run's trajectory: a camera saved as view JSON (`--look-at`, or chosen with `--pick`), one color per body type (bodies with equal node counts), optionally translucent containers.
  - `solvers`: one row per solver of a scene, in the benchmark figures' order: phase shares and ms per sweep from short fixed-budget kernels runs (early exit off: `Solver.<S>.gtol`, `Solver.Convergence.rstol` and `astol` at 0; every solver resumed from the same `--checkpoint-every` checkpoint), then, from full production runs, the per-step stationarity test ratios (as the timeline's) and penetration ratios, sweeps (multiples of the convergence test's interval) and step times. Groups shared by every solver and negligible (`SOLVERS_OMITTED`: Contact update, Residuals, Other) aren't drawn and the bars aren't renormalized. No early exits, by the maintainer's choice: AAAVBD exits early as often as VBD but after fewer sweeps, so the fraction misreads as speed.
  - `scenes`: a LaTeX table of production runs, per scene and solver: step time, iterations, early exits and residual ratios. `slices` writes the fastest/middle/slowest steps' medians as Markdown, for the text.
  - Resumed runs count `--profile-warmup` from the resumed step. A run made in legs (`--resume`, a `--profile-out` per leg) is merged into one result first, `python -m python.tools.sim.profiling.legs leg*.json -o merged.json [--trajectories leg*.h5]` (each leg annotated from its own output; overlapping or mismatched legs are refused): reports and figures key runs by scene and solver, so separate legs would replace each other. The seams' warm-up steps are missing; the timeline draws them as gaps (`step_stats.on_step_grid`).
- **Exclusive vs inclusive.** Stored per-path values (`busy_ms`, `launches`, `union_ms`) are exclusive. `results.inclusive` derives inclusive busy time and launches from path prefixes. Interval unions can't be summed, so inclusive unions (`union_incl_ms`) are computed from raw intervals by the recorder and the nsys importer.
- Tests: `python -m unittest python.tools.sim.gpu.common.profiling`.
